## Unreleased

### English

- **Caller API (branches `-serve-4` to `-serve-6`).** The service takes the actor of every request from the connection only: fs-rpc names the caller of each connection from the system (`SO_PEERCRED` on Unix, the pipe client's token on Windows), `fs-settings-rpc` builds ONE hub per connection (`SettingsService::callers`) and derives the actor `urn:fs:os-user:<Caller::id>`. The ID is the actor (Unix: the uid, Windows: the SID); the account name is display only and may hold spaces. A `by` a client claims is logged (`claimed-by="..." ignored`) and never takes effect; a refused connection is logged, too (both hooks are wired in `build_service` and tested). The command line names its own user the same way (`actor_of_user`: the id from the system, never an argument or an environment variable), so the command line and the service name one user one way (a test compares them on Unix; the Windows SID path is written for the Windows CI and NOT run by the author).
- **Transition (until the contract 0.3, a second cascade).** The contract `settings` 0.2 has no `export`/`import` call and still carries `by` in `admin(by)`. Until 0.3: `export` and `import` work on the database FILE with their own lookup of the process user and refuse (`store-busy`) while a service holds the file; the commands `instance ...` send an empty claim (the service logs `claimed-by="" ignored` once per command). With 0.3 `export` and `import` run through the service, `by` leaves the contract, and the own lookup stays only for `repair` (the emergency path).
- **Pins.** fs-objects v5-4 `3395bf18`, fs-components B1 `81a83e28` (main), fs-rpc and fs-settings-rpc B2-6 `unreviewed/probe-fs-settings-rpc-6` `3d40907d` (on fs-rpc main `c34a4d41`); one source per library.

- Review fixes (branch `-serve-3`): the Windows call `GetUserNameW` takes `&raw mut` (clippy `borrow_as_ptr`, Windows CI); the help and the README no longer name `--by`; a claimed `by` is logged by the service (`claimed-by="..." ignored`, test and mutant). Earlier in this probe: no `--by` (the actor is the OS user of the caller), `import` needs declarations and refuses everything without them (this program has none yet), import in one transaction, no mutex around the store's runtime, tests isolated (own `HOME` and `XDG_*` per run), pins as in the Pins line above (earlier B2-2 `f3f4b374`, now B2-6).

- New program `fs-settings` (probe C of the trait-delta `fs-settings-store`, compiled and tested on Linux): `fs-settings serve` owns the settings database; `DbSettingsStore` implements the port over `fs-objects` `v5::setting`; emergency mode with the visible codes `store-broken` and `store-newer` (the file stays byte-identical); `repair`; `instance set|clear|lock|unlock|log` (reason mandatory, also for unlock; time and OS user set by the service); export and import as TOML and JSON (round trip, one deterministic text); one-time read of the published language files and the frontend choice of fs-tasks (never written, never deleted). No import of `settings.toml` or `instance.toml` (never published). Import runs in one database transaction; the OS user in the log comes from the system, never from an environment variable. `export` and `import` work on the database file and refuse while a service holds it. Windows unchecked by the author: the Windows paths (`GetUserNameW`, `%LOCALAPPDATA%`, `%ProgramData%`) are only compiled by the Windows CI, not run here; dependencies `rustix` 1.1.6 (Unix only, already in the graph through fs-rpc) and `windows-sys` 0.59.0 (Windows only, already in the lock through rustix 0.38).

### Deutsch

- **Caller-API (Zweige `-serve-4` bis `-serve-6`).** Der Dienst nimmt den Akteur jeder Anfrage nur aus der Verbindung: fs-rpc benennt den Anrufer jeder Verbindung aus dem System (`SO_PEERCRED` unter Unix, das Token des Pipe-Clients unter Windows), `fs-settings-rpc` baut EINEN Hub je Verbindung (`SettingsService::callers`) und leitet den Akteur `urn:fs:os-user:<Caller::id>` ab. Die ID ist der Akteur (Unix: die uid, Windows: die SID); der Kontoname ist nur Anzeige und darf Leerzeichen enthalten. Ein vom Client behauptetes `by` wird protokolliert (`claimed-by="..." ignored`) und wirkt nie; eine abgelehnte Verbindung wird ebenfalls protokolliert (beide Haken sind in `build_service` verdrahtet und getestet). Die Befehlszeile benennt ihren eigenen Nutzer genauso (`actor_of_user`: die ID vom System, nie ein Argument oder eine Umgebungsvariable), also nennen Befehlszeile und Dienst einen Nutzer auf eine Weise (ein Test vergleicht sie unter Unix; der Windows-SID-Weg ist für die Windows-CI geschrieben und vom Autor NICHT ausgeführt).
- **Übergang (bis zum Vertrag 0.3, einer zweiten Kaskade).** Der Vertrag `settings` 0.2 hat keinen Aufruf `export`/`import` und trägt `by` noch in `admin(by)`. Bis 0.3: `export` und `import` arbeiten auf der Datenbank-DATEI mit eigener Ermittlung des Prozess-Nutzers und weigern sich (`store-busy`), solange ein Dienst die Datei hält; die Befehle `instance ...` senden einen leeren Claim (der Dienst protokolliert `claimed-by="" ignored` einmal je Befehl). Mit 0.3 laufen `export` und `import` über den Dienst, `by` verlässt den Vertrag, und die eigene Ermittlung bleibt nur für `repair` (Notweg).
- **Pins.** fs-objects v5-4 `3395bf18`, fs-components B1 `81a83e28` (main), fs-rpc und fs-settings-rpc B2-6 `unreviewed/probe-fs-settings-rpc-6` `3d40907d` (auf fs-rpc main `c34a4d41`); eine Quelle je Bibliothek.

- Prüffolgen (Zweig `-serve-3`): der Windows-Aufruf `GetUserNameW` nimmt `&raw mut` (clippy `borrow_as_ptr`, Windows-CI); Hilfe und README nennen `--by` nicht mehr; ein behauptetes `by` wird vom Dienst protokolliert (`claimed-by="..." ignored`, Test und Mutante). Früher in dieser Probe: kein `--by` (Akteur ist der OS-Nutzer des Aufrufers), `import` braucht Deklarationen und lehnt ohne sie alles ab (dieses Programm hat noch keine), Import in einer Transaktion, kein Mutex um die Laufzeit des Speichers, Tests isoliert (eigenes `HOME` und `XDG_*` je Lauf), Pins wie in der Pins-Zeile oben (früher B2-2 `f3f4b374`, jetzt B2-6).

- Neues Programm `fs-settings` (Probe C des trait-delta `fs-settings-store`, unter Linux übersetzt und getestet): `fs-settings serve` besitzt die Einstellungs-Datenbank; `DbSettingsStore` setzt den Port über `fs-objects` `v5::setting` um; Notbetrieb mit den sichtbaren Codes `store-broken` und `store-newer` (die Datei bleibt byte-gleich); `repair`; `instance set|clear|lock|unlock|log` (Grund Pflicht, auch beim Entsperren; Zeit und Betriebssystem-Nutzer setzt der Dienst); Export und Import als TOML und JSON (Rundlauf, ein deterministischer Text); einmaliges Lesen der veröffentlichten Sprachdateien und der Frontend-Wahl von fs-tasks (nie geschrieben, nie gelöscht). Kein Import von `settings.toml` oder `instance.toml` (nie veröffentlicht). Der Import läuft in einer Datenbank-Transaktion; der Betriebssystem-Nutzer im Protokoll kommt vom System, nie aus einer Umgebungsvariable. `export` und `import` arbeiten auf der Datenbankdatei und weigern sich, solange ein Dienst sie hält. Windows ungeprüft: die Windows-Pfade (`GetUserNameW`, `%LOCALAPPDATA%`, `%ProgramData%`) werden nur von der Windows-CI übersetzt, hier nicht ausgeführt; Abhängigkeiten `rustix` 1.1.6 (nur Unix, schon im Graph über fs-rpc) und `windows-sys` 0.59.0 (nur Windows, schon im Lock über rustix 0.38).
