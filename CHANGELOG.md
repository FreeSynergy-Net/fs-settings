# Changelog

Version = tag; all crates of the workspace carry the same version.

## Unreleased

### English

- **CI pin.** `check.yml` and `windows.yml` call fs-release v0.0.18 (`9eed5c95`, was `485f747`): the lock gate of `485f747` still named the old org as the only source of `fs-types` and was red for every repo on the org FreeSynergy-Net.

- **Fix (first main run red).** `build_service` uses `SettingsService::new_os_user_is_person`: fs-settings-rpc v0.0.8 fails closed (every connection a bot, an empty catalog shows a bot nothing: `not-declared`), the transport admits the OS user of the service only, so that user is the person. Behaviour kept: a key that is not declared is still refused for a bot and on import. Written with help from Claude (Anthropic).

- **Module form (SB-6).** `settings/catalog/commands.json` (six commands, bare keys `settings.get|set|reset|lock|unlock|log`, no `id`: the host derives `settings.<key>`) and `settings/catalog/forms.json` (the form `fields-in-groups@1.0.0` for the settings window; "may change" is `RecordView.may`, a human-only setting is not delivered to a bot at all). A second binary `service` (same code as `fs-settings`; `service serve`) is the file the host starts as `<modules>/settings/service`. `serve` starts the heartbeat of fs-rpc (`<socket>.beat`, ticked by the loop of the serving runtime). `fields-in-groups` is only in fs-interfaces main `aa1a58b5` (no tag yet): the test `catalog` reads it from there (dev-dependency `rev`, the normal graph stays on tags). Not yet: the service does not serve `FormSource` (the records of the form), and `settings.*` are not lines of fs-interfaces `capabilities.txt` yet.

- **Caller API (branches `-serve-4` to `-serve-6`).** The service takes the actor of every request from the connection only: fs-rpc names the caller of each connection from the system (`SO_PEERCRED` on Unix, the pipe client's token on Windows), `fs-settings-rpc` builds ONE hub per connection (`SettingsService::callers`) and derives the actor `urn:fs:os-user:<Caller::id>`. The ID is the actor (Unix: the uid, Windows: the SID); the account name is display only and may hold spaces. A `by` a client claims is logged (`claimed-by="..." ignored`) and never takes effect; a refused connection is logged, too (both hooks are wired in `build_service` and tested). The command line names its own user the same way (`actor_of_user`: the id from the system, never an argument or an environment variable), so the command line and the service name one user one way (a test compares them on Unix; the Windows SID path is written for the Windows CI and NOT run by the author).
- **Transition (until the contract 0.3, a second cascade).** The contract `settings` 0.2 has no `export`/`import` call and still carries `by` in `admin(by)`. Until 0.3: `export` and `import` work on the database FILE and refuse (`store-busy`) while a service holds the file (`import --instance` names its own user from the system, `export` needs none; `repair` has no lookup today); the commands `instance ...` send an empty claim (the service logs `claimed-by="" ignored` once per command). With 0.3 `export` and `import` run through the service and `by` leaves the contract; no own lookup is planned then, except possibly for `repair` (the emergency path).
- **Pins.** Tags of the org FreeSynergy-Net: fs-objects v0.0.10, fs-components v0.0.35 (package fs-settings), fs-rpc v0.0.8 (with fs-settings-rpc), fs-types v0.0.6; one source per library; no old-org URL in `Cargo.toml` or `Cargo.lock` (SB-5).

- Review fixes (branch `-serve-3`): the Windows call `GetUserNameW` takes `&raw mut` (clippy `borrow_as_ptr`, Windows CI); the help and the README no longer name `--by`; a claimed `by` is logged by the service (`claimed-by="..." ignored`, test and mutant). Earlier in this probe: no `--by` (the actor is the OS user of the caller), `import` needs declarations and refuses everything without them (this program has none yet), import in one transaction, no mutex around the store's runtime, tests isolated (own `HOME` and `XDG_*` per run), pins as in the Pins line above (earlier B2-2 `f3f4b374`, now B2-7).

- New program `fs-settings` (probe C of the trait-delta `fs-settings-store`, compiled and tested on Linux): `fs-settings serve` owns the settings database; `DbSettingsStore` implements the port over `fs-objects` `v5::setting`; emergency mode with the visible codes `store-broken` and `store-newer` (the file stays byte-identical); `repair`; `instance set|clear|lock|unlock|log` (reason mandatory, also for unlock; time and OS user set by the service); export and import as TOML and JSON (round trip, one deterministic text); one-time read of the published language files and the frontend choice of fs-tasks (never written, never deleted). No import of `settings.toml` or `instance.toml` (never published). Import runs in one database transaction; the OS user in the log comes from the system, never from an environment variable. `export` and `import` work on the database file and refuse while a service holds it. Windows unchecked by the author: the Windows paths (the SID of the process token with `GetTokenInformation`, the account name with `GetUserNameW`, `%LOCALAPPDATA%`, `%ProgramData%`) are only compiled by the Windows CI, not run here; dependencies `rustix` 1.1.6 (Unix only, already in the graph through fs-rpc) and `windows-sys` 0.59.0 (Windows only, already in the lock through rustix 0.38).

### Deutsch

- **CI-Pin.** `check.yml` und `windows.yml` rufen fs-release v0.0.18 (`9eed5c95`, war `485f747`): die Lock-Pruefung von `485f747` nannte noch die alte Org als einzige Quelle von `fs-types` und war fuer jedes Repo der Org FreeSynergy-Net rot.

- **Korrektur (erster main-Lauf rot).** `build_service` nimmt `SettingsService::new_os_user_is_person`: fs-settings-rpc v0.0.8 ist standardmaessig geschlossen (jede Verbindung ein Bot, leerer Katalog zeigt einem Bot nichts: `not-declared`); der Transport laesst nur den OS-Nutzer des Dienstes zu, dieser ist die Person. Unveraendert: ein nicht deklarierter Schluessel wird fuer einen Bot und beim Import weiter abgelehnt. Geschrieben mit Hilfe von Claude (Anthropic).

- **Modul-Form (SB-6).** `settings/catalog/commands.json` (sechs Befehle, nackte Schlüssel `settings.get|set|reset|lock|unlock|log`, keine `id`: der Host bildet `settings.<Schlüssel>`) und `settings/catalog/forms.json` (die Form `fields-in-groups@1.0.0` für das Einstellungs-Fenster; „änderbar“ ist `RecordView.may`, eine Nur-Mensch-Einstellung wird einem Bot gar nicht ausgeliefert). Ein zweites Binary `service` (derselbe Code wie `fs-settings`; `service serve`) ist die Datei, die der Host als `<modules>/settings/service` startet. `serve` startet den Herzschlag von fs-rpc (`<socket>.beat`, getaktet von der Schleife der Laufzeit). `fields-in-groups` steht nur in fs-interfaces main `aa1a58b5` (noch kein Tag): der Test `catalog` liest es von dort (Dev-Abhängigkeit mit `rev`, der normale Graph bleibt auf Tags). Noch nicht: der Dienst liefert kein `FormSource` (die Datensätze der Form), und `settings.*` sind noch keine Zeilen von `capabilities.txt` in fs-interfaces.

- **Caller-API (Zweige `-serve-4` bis `-serve-6`).** Der Dienst nimmt den Akteur jeder Anfrage nur aus der Verbindung: fs-rpc benennt den Anrufer jeder Verbindung aus dem System (`SO_PEERCRED` unter Unix, das Token des Pipe-Clients unter Windows), `fs-settings-rpc` baut EINEN Hub je Verbindung (`SettingsService::callers`) und leitet den Akteur `urn:fs:os-user:<Caller::id>` ab. Die ID ist der Akteur (Unix: die uid, Windows: die SID); der Kontoname ist nur Anzeige und darf Leerzeichen enthalten. Ein vom Client behauptetes `by` wird protokolliert (`claimed-by="..." ignored`) und wirkt nie; eine abgelehnte Verbindung wird ebenfalls protokolliert (beide Haken sind in `build_service` verdrahtet und getestet). Die Befehlszeile benennt ihren eigenen Nutzer genauso (`actor_of_user`: die ID vom System, nie ein Argument oder eine Umgebungsvariable), also nennen Befehlszeile und Dienst einen Nutzer auf eine Weise (ein Test vergleicht sie unter Unix; der Windows-SID-Weg ist für die Windows-CI geschrieben und vom Autor NICHT ausgeführt).
- **Übergang (bis zum Vertrag 0.3, einer zweiten Kaskade).** Der Vertrag `settings` 0.2 hat keinen Aufruf `export`/`import` und trägt `by` noch in `admin(by)`. Bis 0.3: `export` und `import` arbeiten auf der Datenbank-DATEI und weigern sich (`store-busy`), solange ein Dienst die Datei hält (`import --instance` ermittelt seinen Nutzer selbst vom System, `export` braucht keinen; `repair` hat heute keine Ermittlung); die Befehle `instance ...` senden einen leeren Claim (der Dienst protokolliert `claimed-by="" ignored` einmal je Befehl). Mit 0.3 laufen `export` und `import` über den Dienst und `by` verlässt den Vertrag; dann ist keine eigene Ermittlung geplant, höchstens für `repair` (Notweg).
- **Pins.** Tags der Org FreeSynergy-Net: fs-objects v0.0.10, fs-components v0.0.35 (Paket fs-settings), fs-rpc v0.0.8 (mit fs-settings-rpc), fs-types v0.0.6; eine Quelle je Bibliothek; keine alte Org-URL in `Cargo.toml` und `Cargo.lock` (SB-5).

- Prüffolgen (Zweig `-serve-3`): der Windows-Aufruf `GetUserNameW` nimmt `&raw mut` (clippy `borrow_as_ptr`, Windows-CI); Hilfe und README nennen `--by` nicht mehr; ein behauptetes `by` wird vom Dienst protokolliert (`claimed-by="..." ignored`, Test und Mutante). Früher in dieser Probe: kein `--by` (Akteur ist der OS-Nutzer des Aufrufers), `import` braucht Deklarationen und lehnt ohne sie alles ab (dieses Programm hat noch keine), Import in einer Transaktion, kein Mutex um die Laufzeit des Speichers, Tests isoliert (eigenes `HOME` und `XDG_*` je Lauf), Pins wie in der Pins-Zeile oben (früher B2-2 `f3f4b374`, jetzt B2-7).

- Neues Programm `fs-settings` (Probe C des trait-delta `fs-settings-store`, unter Linux übersetzt und getestet): `fs-settings serve` besitzt die Einstellungs-Datenbank; `DbSettingsStore` setzt den Port über `fs-objects` `v5::setting` um; Notbetrieb mit den sichtbaren Codes `store-broken` und `store-newer` (die Datei bleibt byte-gleich); `repair`; `instance set|clear|lock|unlock|log` (Grund Pflicht, auch beim Entsperren; Zeit und Betriebssystem-Nutzer setzt der Dienst); Export und Import als TOML und JSON (Rundlauf, ein deterministischer Text); einmaliges Lesen der veröffentlichten Sprachdateien und der Frontend-Wahl von fs-tasks (nie geschrieben, nie gelöscht). Kein Import von `settings.toml` oder `instance.toml` (nie veröffentlicht). Der Import läuft in einer Datenbank-Transaktion; der Betriebssystem-Nutzer im Protokoll kommt vom System, nie aus einer Umgebungsvariable. `export` und `import` arbeiten auf der Datenbankdatei und weigern sich, solange ein Dienst sie hält. Windows ungeprüft: die Windows-Pfade (die SID des Prozess-Tokens mit `GetTokenInformation`, der Kontoname mit `GetUserNameW`, `%LOCALAPPDATA%`, `%ProgramData%`) werden nur von der Windows-CI übersetzt, hier nicht ausgeführt; Abhängigkeiten `rustix` 1.1.6 (nur Unix, schon im Graph über fs-rpc) und `windows-sys` 0.59.0 (nur Windows, schon im Lock über rustix 0.38).
